# Canvas Demo：九条可操作 CUJ

目的：验证用户意图如何变成持久化模型变更，再驱动画布更新。默认使用确定性 mock，无需 API key。

```sh
cd canvas-demo
npm ci --omit=dev
npm start
# 打开 http://127.0.0.1:4317
```

页面包含组件列表、画布、属性编辑器、评论、agent 输入和事件查看器。每次成功提交，revision 增加，画布从服务端已提交模型重新渲染。以下流程可以连续体验；卡片上限为 8 张，至少保留 1 张。

## 1. 直接修改画布里的文字

1. 选中一张卡片，再双击标题或正文；也可以点击卡片上的 **Edit text** 编辑正文。
2. 在弹窗里输入新内容并提交。
3. 在模型查看器找到相同组件 ID；查看最新提交事件的 diff。

预期：只修改指定组件的 `title` 或 `body`。组件 ID 不变；输入 `<b>Hello</b>` 会作为普通文字显示，不会执行 HTML。取消弹窗不会提交。右侧属性编辑器仍支持同时修改标题、正文、颜色后统一提交。

数据路径：`set_text(componentId, nodeId, text, baseRevision)` → 服务端字段和长度校验 → snapshot/diff blobs → `workspace.edit_committed` → SSE → 画布。输入时的每个按键不是独立持久化事件，一次提交才是一笔事务。

## 2. 新建、复制并制作一个变体

1. 点击 **New card**，观察新增默认卡片。
2. 选中已有卡片，点击 **Duplicate**。
3. 修改副本的标题或颜色，检查原卡片未变化。

预期：新建和复制都生成新的稳定 ID；副本插在原卡片后面。复制内容不复制 ID，也不继承原卡片评论。达到 8 张时按钮禁用，服务端也执行同样的容量约束。

事件记录 `intent.operation = create / duplicate`，前后 snapshot 和确定性 diff 记录实际结果。相同 commandId、相同输入重试只提交一次，重启后仍有效；复用同一 commandId 携带不同输入会失败。当前浏览器每次新操作生成新 commandId，没有实现自动网络重试 UI。

## 3. 调整阅读顺序

1. 选中非首尾位置的卡片。
2. 点击 **Move earlier** 或 **Move later**。
3. 同时观察画布、左侧列表和模型数组顺序。

预期：只改变 `components` 的顺序，内容和 ID 不变。首尾边界按钮禁用；非法越界请求也被后端拒绝。diff 中有 `component-order` 变化。点击 Undo 可恢复原顺序。

这是文档顺序编辑；尚未实现自由拖拽坐标或响应式布局规则。

## 4. 删除组件，再撤销与重做

1. 给某张卡片添加评论，确保画布至少有两张卡片。
2. 点击 **Delete**，该卡片从画布消失。
3. 点击 **Undo**，重新选中恢复的卡片。
4. 检查 ID、文字、颜色、位置和原评论，再点击 **Redo**。

预期：撤销恢复原组件及其身份；评论事件仍在历史中，恢复该 ID 后又可见。重做再次删除。最后一张卡片无法删除。

撤销、重做各追加一笔新 revision，不删除或改写旧事件。删除本身不删除历史评论或 blobs；这不是隐私擦除接口。撤销后执行新编辑，会清空可重做分支。

## 5. 评论一个节点，再让 agent 修改

1. 选中卡片，在评论区域选择 `title` 或 `body` 锚点。
2. 输入 `change color` 并保存评论。
3. 评论列表显示节点及评论时 revision。点击 **Use as agent instruction**。
4. 检查 agent 输入框，选择 mock，点击运行。

预期：复制评论到输入框本身不调用模型、不提交模型变化。运行后 mock 改变当前选中卡片颜色；评论保留。mock 只识别少数固定规则，不理解任意自然语言。

评论事件保存 `component_id`、`node_id`、`revision` 和文字。agent 上下文包含当前 snapshot、最近三次结构化修改与最近六条评论。历史锚点不被偷偷改成最新 revision。当前没有评论线程、解决状态或旧评论语义自动迁移；切换组件后运行会作用于新的选中组件，因此运行前应检查选择。

## 6. 两个窗口同时编辑：拒绝覆盖，保留草稿

1. 在两个标签页 A、B 打开同一地址。
2. A 打开文字编辑弹窗，输入草稿，但先不提交。
3. B 修改同一组件并提交，A 背后的画布会收到最新状态。
4. A 提交旧弹窗里的草稿。

预期：服务端返回 revision conflict；A 的弹窗仍打开，输入文字仍在，B 的提交未被覆盖，也不新增一次成功编辑事件。

冲突后先复制草稿，关闭弹窗，再打开最新组件，人工合并后提交。当前没有自动三方合并。版本检查是整个工作区粒度：即使 B 改的是另一张卡片，也会使 A 的旧版本提交失败。

## 7. 人与 agent 共用撤销历史

1. 人工把标题改成 A，提交。
2. mock 输入 `标题：B` 并运行。
3. 点击画布空白区域，再按 Ctrl/Cmd-Z；标题恢复为 A。
4. 再撤销一次，回到人工编辑前。Ctrl/Cmd-Shift-Z 重做。

预期：人和 agent 走同一模型提交历史，无需两个 Undo 系统。输入框和文字弹窗内保留原生输入撤销，不触发已提交事务撤销。

撤销作用于最新可撤销事务，不是“只撤销我的操作”；多人场景下的选择性撤销尚未实现。评论和请求审计事件不属于组件编辑撤销栈。

## 8. 重启后继续编辑

1. 完成新建、排序和文字修改，记下 revision 与组件 ID。
2. 正常停止服务器，再在相同目录运行 `npm start`。
3. 刷新页面并检查模型与顺序。

预期：通过事件链与 blobs 重建同一状态，再生成 `.data/workspace/` 投影。手工修改生成的 HTML 不属于支持的编辑入口，重启会覆盖它。

本地单进程持有 writer lock；不要同时启动两个进程写同一数据目录。硬崩溃后的锁需要确认旧进程退出后人工清理。本流程验证正常重启，不代表完成断电或分布式恢复验证。

## 9. 从 UI 行为追到日志与模型请求

1. 提交一次直接编辑，点击对应提交事件，查看 intent、snapshot 引用和展开的 diff。
2. 运行一次 mock，点击请求事件，查看重建请求与 assertion。
3. 不勾选 capture 运行一次，再勾选后运行一次，对比请求事件引用。
4. 导出 trajectory 文件。

预期：默认不额外存完整 request body blob，但可重建所必需的输入、配置等片段仍会落盘。`assert=true` 是从磁盘重建后实际比较成功的结果。capture 只控制额外完整请求快照，不关闭片段持久化或验证。导出包含原始 JSONL 与所有 blobs，不能只有可读摘要。

UI 只展示最近 12 条事件按钮；完整历史仍在导出中。真实 Codex 路径验证的是网关实际收到的 Responses HTTP 请求；mock 的成功不能替代真实 provider 验收。

## API 与验收范围

新增入口 `POST /api/component` 复用现有 session token 和 origin 检查。公共字段为 `operation`、`commandId`、`baseRevision`；组件操作使用 `componentId`；`set_text` 另带 `nodeId`、`text`；`move` 另带 `direction: -1 | 1`。

| 验收点                                         | 覆盖                                    |
| ---------------------------------------------- | --------------------------------------- |
| 新建 → 复制 → 改字 → 排序 → 删除 → Undo/Redo   | HTTP 集成测试，包含导出与生成 HTML 检查 |
| 同一命令重试、重启后重试、命令 ID 冲突         | 持久化命令测试                          |
| 旧 revision、非法节点、超长文字                | 拒绝写入且状态保持不变                  |
| 至少一张、最多八张、排序边界                   | 服务端约束测试                          |
| 原有事件恢复、请求重建、gateway、Codex fixture | 原有测试保持通过                        |

共 15 项 Node 测试通过。浏览器实际双击、焦点、快捷键和视觉布局未完成浏览器自动化验收；以上是可人工执行的验收步骤。真实付费模型和 Electron 安装包也尚未端到端验证。


新增 HTML 组件的完整流程和最新验收状态见 [HTML CUJ](HTML-CUJ.zh-CN.md)。上述 15 项是原版卡片测试范围；当前后端共 17 项通过，桌面 UI 尚待独立验收。
